This reference describes the implemented engine contract. `Invoke-Migration` accepts native PowerShell hashtables or other PowerShell objects for step definitions; examples use hashtables. It does not claim full KingswaySoft or SSIS compatibility.

Each migration database has one process owner, started implicitly by the first module caller or explicitly with `Start-MigrationDatabaseServer`. Separate callers route store operations through same-user local IPC; schedulers, workers, connections, and callbacks remain caller-side. Multiple run IDs can use the same database, while per-run leases prevent duplicate schedulers for a single run.

Source readers receive a `MigrationStepCheckpoint` with `LastCompletedSequence` and `CursorJson` for the last contiguous completed batch, and `ResumeSequence` and `ResumeCursorJson` for the latest durably enqueued batch. Readers should continue after the resume position; pending and in-flight batches are replayed from SQLite using their stored payloads.

`Inputs` declares row-flow dependencies. A source can name one or more keyed parent-source inputs using explicit `{ Child, Parent }` column pairs; a JSON null child key means that relationship is absent and the row is retained without waiting for that parent. Unmatched non-null keys fail the run. `RowsPerParent` can enforce a fixed child count independently for each parent relationship. Row-linked child records are staged in temporary SQLite storage and do not need to be pre-sorted. `DependsOn` is completion-only and accepts step IDs. A `join` node combines exactly two ordered inputs using explicit aliases and ordered single- or composite-key pairs; its parent may be a Source or a Dataverse Target. Target parent keys must match an ordered `Options.MatchOn` group; Source parent keys must be present and unique. Joins can be chained for additional lookups, including dotted paths into nested joined rows. They require an explicit `inner` or `left` type. Join rows are indexed in SQLite as batches complete; `JoinOrder` defaults to `ready`, emitting available matches even when an earlier child row is waiting for its parent, so outputs may be reordered. Set `JoinOrder = 'stable'` to preserve left-input order; this can delay later matches behind an earlier unresolved key. Null keys never match, and neither side must be sorted by join key. A Source using `DependsOn` can instead reread completed Dataverse parent rows before downstream work begins, trading extra reads for whole-step sequencing. Root sources must be ordered by `Key`. Dataverse Simple queries apply that order when `OrderBy` is omitted; SQL and custom readers must provide it. SQLite and DuckDB sources execute caller-supplied ordered queries through their ADO.NET connections. SQLite and DuckDB targets auto-create output tables by default or can validate explicit schemas; writes are transactional and replay-safe. Dataverse Targets support alternate-key matching, per-target batch-size experiments scored against whole-pipeline successful output throughput, and a shared adaptive concurrency budget per connection. The scheduler uses graph-impact weights and current ready backlog to favor work with more pipeline impact while preserving weighted fairness. Retry and throttle signals are observed when connection logging supports them; retries remain enabled normally, with `-DataverseNoRetryDiagnosticMode` available for diagnostics. Tuning profiles are versioned, persisted in the run database, and reused subject to connection identity and current limits; use `Clear-MigrationTargetTuning` to clear profiles. See [migration dependencies](./concepts/dependencies.md), [step configuration](./configuration.md), [SQLite connectors](./connectors/sources/sqlite.md), [DuckDB connectors](./connectors/sources/duckdb.md), and the [Dataverse target](./connectors/targets/dataverse.md).

Progress is measured per step from queued standard `Records` batches. SQLite and DuckDB derive counts by wrapping their source `Options.Query` (an explicit `Options.CountQuery` may override this); Simple and FetchXML Dataverse sources use `Get-DataverseRecord -TotalRecordCount`; custom PowerShell sources may provide a `Custom.CountCallback`; and Parquet sources use file metadata. These provide totals without streaming records to count them. Other sources may set `ExpectedRecordCount` explicitly or leave the total unknown until rows flow. A positive explicit `ExpectedRecordCount` takes precedence over a provider and, like a resolved provider count, is checked against the source rows when enumeration completes. Transform and Filter steps may emit zero, one, or multiple rows, and inner Joins may filter inputs, so downstream totals are based on their actual materialized input batches. A target's percentage is available only after all of its inputs are finalized and its batches are countable. Custom payloads without a `Records` array remain uncounted. Run-level target totals sum target-write work across targets, not unique logical source rows.

CSV sources detect the input file's `LF`, `CRLF`, or `CR` record separator automatically; the CSV `NewLine` option controls output formatting.

When debug capture is enabled, custom callback stages can map output rows to inputs in the current batch with `MigrationDebugStage.ParentRecordIndices` or to rows in distinct dependency batches with `MigrationDebugStage.ParentRecordReferences`. `StoredBatch.ParentBatchIds` exposes those direct parent batches to callbacks. See the [dashboard guide](./cmdlets/migration-dashboard.md) for lineage behavior and retention details.
